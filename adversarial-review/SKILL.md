# 对抗式审查

完成不等于可用。交付前切换到反方立场，以"推翻这个方案"为目标发起攻击，找到最有杀伤力的那一点，修复它或明确说明为什么接受这个风险。

## 何时使用

- 方案、设计、代码、文章刚完成，准备交付前
- 用户要求把关："审查一下""挑挑毛病""会不会翻车"
- 修复了一个问题之后（新改动可能引入新问题）
- 结论重大、出错代价高（删除操作、资损、安全）

## 操作步骤

1. **重申论点**。用一句话写出待审对象的主张："这个方案能成立，是因为……"
2. **转换立场**。接下来只做一件事：证明上面这句话是错的。扮演最有动机推翻它的角色——被这个方案伤害的用户、要接手维护的工程师、被忽略的并发/边界/恶意输入。
3. **发动攻击**。按杀伤力排序列出最强反驳，每条写明攻击路径（什么条件下、经过哪一步、导致什么后果）。目标是找到"一击致命"的那条，不是罗列小毛病。
4. **裁决**。对每条反驳判定：成立概率多大、影响多大、修复成本多大。
5. **处置**。高影响项当场修复后重审（修复本身也要被攻击一轮）；低影响项写明接受理由，随交付物一起呈现。

完成标准：输出中有"最强反驳 + 判定 + 处置结果"；被修复的问题注明修复后重审过。

## 标志性追问

- "如果我要证明它会失败，我会从哪里下手？"
- "最坏情况下会怎样？最坏情况离现实有多远？"
- "反方能举出一个我无法回应的例子吗？"

## 失败模式

- 走过场式自查：列的都是无关痛痒的小问题。检验方法：看完清单自问"哪一条会让方案失败"——答不出来就是没审到位。
- 只审不改：发现问题后原样交付。发现即处置，处置不了的说明原因。
- 忽略修复引入的新问题：每次修复都可能带来新风险，重大修复需要再过一轮。

## 示例

- Before："分页用 limit/offset 就行了。"交付。
- After：反方攻击——数据在写入时 offset 分页会漏行/重行；大 offset 时查询变慢。判定：管理后台写入频率低、数据量小，接受；面向用户的 feed 流，改为游标分页。
