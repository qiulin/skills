# 第一性原理

回到事实本身推导方案：先剥离类比、惯例和想当然的假设，把问题还原为不可再分的约束，再从约束出发重新构建答案。

## 何时使用

- 用户问"为什么这样设计""本质是什么""有没有更好的办法"
- 沿用现有做法只是因为"大家都这么做/一直这么做"
- 方案选型、技术选型，需要判断哪些约束是真的、哪些是习惯
- 需求模糊，表面诉求背后有更根本的目标

## 操作步骤

1. **写下表面问题和默认方案**。用一句话表述"现在打算怎么做、因为什么"。
2. **列出隐含假设**。把支撑默认方案的所有前提写出来，每条以"必须有…/大家都知道…/一直都是…"开头。目标是把没说出口的信念全部摆上桌面。
3. **逐条审问假设**。对每条问三个问题：它是被验证过的事实，还是传承下来的惯例？它能被什么证据推翻？拿掉它问题还成立吗？
4. **还原为硬约束**。只保留经得起审问的事实（物理规律、数学性质、已确认的业务硬指标、已验证的用户行为），其余降级为可选项。
5. **从硬约束重新推导**。只基于硬约束构建方案，再与默认方案对比：相同，说明默认方案恰好合理；不同，说明之前被假设带偏了。

完成标准：输出中有一份假设清单（每条标注"事实/惯例"）和一条只基于事实推导出的方案。

## 标志性追问

- "这个前提是被证明的，还是被继承的？"
- "如果这条不成立，问题会变成什么样？"
- "没有这个领域惯例的外行，会怎么解决这个问题？"

## 失败模式

- 把惯例当事实：用"行业都这么做"替代论证。惯例最多是线索，要问它最初为什么出现、现在是否还成立。
- 还原不到位：停在"第二层原因"就开推。追问到无法再问"为什么"为止。
- 为不同而不同：从事实推导出的方案与默认方案一致时，就承认一致——强行标新立异违反第一性原理本身。

## 示例

- Before："接口慢，加一层 Redis 缓存。"（惯例：慢 = 加缓存）
- After：审问假设——慢在哪一步？测得一条 SQL 全表扫描 800ms。"必须有缓存"降级为惯例；硬约束是查询按主键可命中、返回 20 行。从事实推导：加索引把 800ms 降到 3ms，不需要引入缓存一致性问题。
