# 深度复查（Rethink）

一次产出只是当前视野下的最优解。被要求"再想想"时，动作是换更宽的视角、下更深的层级，找出该修正的、该补充的；复查后确实站得住，就明确说结论不变——复查的价值在于可信度，不在于产出量。

## 何时使用

- 用户说"再想想""再深入分析""再全面一点""还有吗"
- 交付的方案/分析即将进入执行，值得多过一轮
- 自己对刚交付的内容留有"似乎浅了"的直觉
- 与对抗式审查的分界：找致命伤用对抗式审查；扩大覆盖面和深度用本 skill

## 操作步骤

1. **重建覆盖范围声明**。重读原产出，写出它声称覆盖了什么：回答的问题、考虑的维度、依赖的假设。复查对象是声明之外的空白，和声明之内的薄弱处。
2. **横向扩面：至少换两个没用过的新视角**。视角重置失败是复查最常见的空转——用原视角再看只会得到原结论。常用视角：
   - 边界与极端：数据量为 0 / 极大、并发、恶意输入
   - 时间轴：一周后、一年后、出问题时（维护、演进、回滚）
   - 利益相关方：运维、下游调用方、合规、新接手的工程师
   - 替代方案：当初没选的那几个，真的是被硬约束排除的吗
3. **纵向下钻：找"停在第一层"的结论**。逐条问：这是根因还是现象？断言有量化或出处吗？"应该/大概"背后藏着什么没验证的假设？对最薄弱的 1-2 处继续追问到事实层。
4. **分诊输出，三类各归其位**：
   - 修正项——原产出有错：写明错在哪、正确的是什么、依据；
   - 补充项——有价值的遗漏：写明为什么重要、最小可行版本是什么；
   - 维持项——复查过但站得住：点名"已复查，结论不变"，附一句理由。
5. **诚实收尾**。真找不到问题，就明确说"从 X、Y 视角复查过，结论不变"，并列出复查过的维度。信息量为零的"整体不错，还可以更深入"比不复查更糟。

完成标准：输出是一份修正/补充/维持的分诊清单，每项带依据；没有修正和补充时，明确列出复查过的视角并声明结论不变。

## 标志性追问

- "这个结论在什么边界之外不成立？"
- "哪个受影响的人/系统没出现在分析里？"
- "这是根因，还是根因的现象？"
- "去掉最核心的那个假设，结论还剩多少？"

## 失败模式

- 为改而改：制造不痛不痒的修改来显得有产出。改的判据是"它解决真实的问题"，不是"我得说点新东西"。
- 加长不等于深化：字数和列表变多、信息量不变，是负产出。每段新增内容都要能回答"删掉它读者会损失什么"。
- 全盘重写：复查发现局部问题就推翻整个产出。分诊的意义就是只动该动的部分。
- 视角空转：用原有视角复述原结论。开始前列出本次要用的、之前没用过的视角。

## 示例

- Before：用户："这个迁移方案再全面分析一下。"→ 复述原方案，补几句"注意备份"。
- After：覆盖声明是"停写、迁移、切读"。换视角下钻发现：①修正——"无需回滚脚本"不成立，DDL 扩列不可逆，补回滚预案；②补充——双写期间的延迟尖刺会触发既有告警阈值，提前调整阈值或加静默窗口；③维持——容量估算复核过，口径正确。收尾："两处需改，其余复查无变化。"
