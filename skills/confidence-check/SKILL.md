# 列出不自信点

交付前把"我没把握的地方"主动摊开：宁可暴露不确定性让用户多问一句，也不让一个没验证的断言混在结论里被当成事实带走。

## 何时使用

- 交付前自查：答案、方案、报告、评审意见即将发给用户
- 结论里包含记忆型事实（API 签名、版本号、配置默认值、统计数字）
- 用户追问"你确定吗""有没有坑""风险是什么"
- 结论会驱动用户的决策（选型、上线、花钱）

## 操作步骤

1. **重读交付物，逐条标注置信度**。把每个事实性断言分为三档：
   - 已验证——本次会话中读过源码/文档/运行结果确认过；
   - 高置信推断——有依据但未直接验证；
   - 存疑——凭印象、凭经验、可能过时。
2. **挑出最没把握的 3-5 点**。优先级 = 影响大 × 置信度低。每点写两句：不确定的是什么；怎么验证（查哪份文档、跑哪个命令、问哪个人）。
3. **置顶呈现**。放在交付物的显著位置逐条列出，语气直接："这两点我没把握"，而不是"可能存在一定风险"。
4. **能当场验证的当场验证**。列出不确定点后，先用工具验证其中可验证的（读源码、查文档、跑命令），验证完的升级为已验证或降级为错误，剩余的才留给用户。

完成标准：交付物附带不确定点清单，每点可追溯到验证途径；"我不确定"以原话出现，而不是被措辞稀释掉。

## 标志性追问

- "这句话我是刚验证过，还是长期记忆里的印象？"
- "如果这一点错了，用户的下一个动作会付出什么代价？"
- "我有没有为了显得流畅而略过了拿不准的细节？"

## 失败模式

- 流畅掩盖无知：编造 API 名、版本号、统计数据来维持回答的连贯。宁可说"这里我需要查证"。
- 清单走过场：列了不确定点但不分优先级，和没列一样。挑影响最大的几条。
- 把不确定写成免责声明："可能、也许、大概"撒一篇文章是噪音；点名哪几条、为什么、怎么办才是信息。

## 示例

- Before："升级到 v3 后配置项 A 默认会变，注意一下。"（默认值凭印象，但听起来像已确认事实）
- After："两点我没把握：① v3 中 A 的默认值——我记得改为 true，未查证，升级前先看官方 changelog 确认；② 迁移耗时估计 20 分钟——按数据量拍的，建议先在预发跑一次。"
