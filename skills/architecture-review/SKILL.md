# 项目评审（Architecture Review）

完整项目的评审靠一个会话从头读到尾，读到最后前面已经模糊。正确姿势：原会话建立全局理解并切分模块，模块评审并行派发（范围互不重叠，无需隔离），发现汇总后**逐条复核**——子代理的发现是自述，不是证据。

## 何时使用

- 用户要求评审完整项目的架构设计和实现
- 接手陌生项目，需要系统性摸底
- 大重构或大版本启动前，全面检查当前状态

## 操作步骤

**阶段一：理解与切分（原会话）**

1. **建立项目画像**。读入口、配置、依赖清单、文档，跑通构建与测试（只读操作，评审全程零代码改动），产出：技术栈与分层、模块草图及职责、核心数据流、外部依赖与部署形态。画像写进后续每个子代理的 prompt——全局理解只做一次，它们不重复摸索。
2. **划分模块**。按职责/变化原因切（同 high-cohesion-low-coupling 的切法），不是照目录机械对应。每个模块写清边界（文件清单）、对外接口、依赖方向；规模以一个子代理能吃透为限（通常 2-6 个）。
3. **单列横切评审**。模块级看不到的问题单独立项：模块间数据流与集成约定、事务边界、全局架构决策、配置与部署一致性。原会话自己做，或单派一个子代理。

**阶段二：分模块评审（子代理，并行）**

4. **生成评审 prompt**（自足）：项目画像 + 模块边界与文件清单 + 评审维度 + 统一发现格式 + 证据要求（每条发现必须带 文件:行 与代码摘录，无证据的降标"待复核"）+ 零改动约束（可跑测试与构建，不可修改代码）。
5. **评审维度**（按项目画像裁剪）：
   - 功能性：逻辑错误、边界条件、异常路径、实现与设计意图的偏差
   - 性能：复杂度、N+1 与重复 IO、内存、并发与锁
   - 安全性：注入、鉴权与越权、密钥硬编码、依赖漏洞、反序列化
   - 可维护性：职责与耦合、重复、命名、与整体架构的一致性
   - 可靠性：错误处理、失败恢复、资源泄漏、超时与重试
   - 可观测性：日志与指标、出错后能否定位（按项目形态取舍）

   统一发现格式：`[维度][高/中/低] 标题 / 位置（文件:行）/ 证据（代码摘录）/ 影响 / 建议`。

**阶段三：汇总与复核（原会话）**

6. **汇总去重**。全部发现进一张总表，按 严重度×维度×模块 归类；不同模块报出的同一根因合并——跨模块问题往往在这里现形。
7. **逐条复核**。自述不是证据：高严重度逐条打开代码核实；中低严重度抽查，存疑标"待验证"；误报剔除并记录理由；同步校准严重度（子代理常夸大或低估）。
8. **产出最终报告**：项目画像 → 架构总评（优点、风险、技术债）→ 确认的发现清单（位置/证据/影响/建议，按 影响×修复成本 排序）→ 机制层建议（同类问题多处出现时，按 mechanism-gap 建议机制补齐而非逐点修）→ 建议的行动顺序。

完成标准：项目画像 + 每模块发现（带证据）+ 复核记录（确认/剔除/降级，含理由）+ 最终报告（排序的发现清单 + 机制层建议）。

## 标志性追问

- "模块边界是按职责切的，还是照着目录抄的？"
- "这条发现有代码证据吗？我打开看过吗？"
- "几个模块报的同一个问题，根因在哪个模块？"
- "同类问题在多处出现——逐个修，还是机制补齐？"

## 失败模式

- 画像缺失就派发：子代理各自摸索全局，口径不一且重复浪费。全局理解只做一次，写进每个 prompt。
- 照目录切模块：目录不等于职责，边界重叠和空白都会制造漏评。按变化原因切，文件清单写清。
- 复核形同虚设：汇总即终稿。子代理会误报、夸大、看走眼——高严重度必须逐条亲手核实。
- 只列问题不排序：几十条平铺的发现等于没有报告。优先级 = 影响 × 修复成本，行动顺序要给出来。
- 评审顺手改代码：评审零改动，改善建议进报告；想动手的部分转化为后续任务。

## 与相关 skill 的衔接

- 模块切分原则来自 high-cohesion-low-coupling；机制层建议来自 mechanism-gap；
- 评审报告可按 design-doc 落盘为项目文档；
- 确认的修复任务可走 design-only → handoff-implement 流水线逐项解决。

## 示例

- Before：用户："全面评审一下这个项目。"
- After：原会话跑通构建与测试，画像是"三层 Web 服务 + 两个内部包"，按职责切 4 个业务模块 + 1 个横切（数据流与事务边界）；5 个子代理并行按六维度评审，按统一格式返回 23 条发现。汇总去重后余 20 条；复核：3 条高严重度逐条核实——2 条确认、1 条误报剔除（子代理看漏了调用方的空值保护，理由已记录）；两个模块分别报的"超时未设置"合并为横切问题，根因在公共 HTTP 客户端 → 机制建议：客户端统一默认超时，而非逐处加参数。最终报告按 影响×修复成本 排序，首推事务边界缺失的修复。
