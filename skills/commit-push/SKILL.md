# 提交推送（Commit Push）

提交的范围是本会话的足迹，不是整个工作区。工作区里常有不属于你的并行修改（用户手改、其他会话、工具产物）——它们不是你的提交材料，但可能与本次提交相互影响；影响与否判定不了的，由用户裁决。

## 何时使用

- 用户说"提交推送""commit""提交代码"
- 一段工作完成，本会话的改动需要入库
- 工作区混杂多个来源的改动，需要范围化提交

## 操作步骤

1. **盘点会话足迹**。列出本会话实际创建、修改、删除、重命名的文件（来自自己的操作记录，不凭印象）。会话没有改过任何文件时，到此为止，如实告知无东西可提交。
2. **对照工作区分类**。`git status --short` 的每一项归入三类：
   - **会话改动**——在足迹清单里，是本次提交的材料；
   - **并行改动**——不在足迹里的已修改/未跟踪文件（用户手改、其他会话产物）；
   - **工具产物**——本地状态文件（agent 配置、计划缓存等），默认不入库，必要时建议加 .gitignore。
3. **判定并行改动的影响**。对每个并行改动问两个问题：
   - **同文件混叠**：我的足迹文件里，是否混入了不是我写的改动（diff 里有陌生的块）？
   - **语义依赖**：不带它的改动，我的提交能否独立成立（构建过、测试绿、引用的接口/配置完好）？
   判定**不影响** → 不碰它，原样留在工作区；判定**影响或无法判定** → 列出选项交用户裁决（整文件带上 / `git add -p` 拆分 / 暂缓提交）。替用户做这个决定是越权。
4. **按路径暂存**。只 `git add <具体路径>`，禁止 `git add .` / `-A`；暂存后 `git diff --cached --stat` 核对：暂存清单必须与会话足迹（含用户裁决结果）完全一致，多一个少一个都查清再走。
5. **提交并推送**。commit message 概括本会话的改动内容（做什么，不是流水账）；push 单独执行，不与其他命令串联；被拒（远程有新提交）不 force、不反复硬试，报告用户。
6. **复核收尾**。push 后确认分支与远程同步（ahead 0）；向用户报告三件事：提交了什么、工作区还留着哪些并行改动、推送结果。

完成标准：提交中每个文件都属于会话足迹或用户裁决；并行改动原样保留且被明确报告；push 后本地与远程同步。

## 标志性追问

- "这个文件是我这个会话改的吗？"
- "工作区里还有哪些改动不是我做的？"
- "不带它的改动，我的提交能独立成立吗？"
- "暂存清单和会话足迹完全一致吗？"

## 失败模式

- `add .` 一把梭：把用户未完成的并行修改、临时产物、密钥配置一起提交。暂存是按路径点名，不是清扫工作区。
- 足迹凭印象：不对照 git status 就断言"都是我的改动"，漏掉混叠的外来修改。
- 影响误判为无关：不带并行改动会导致本次提交构建失败或语义残缺——这就是影响，交用户裁决，不是自行取舍。
- push 被拒硬刚：远程有新提交说明别人先行，force 或反复重试都会踩别人的工作。报告用户。
- 推送即宣布完成：不看 ahead/behind 就收工，推送静默失败都不知道。

## 示例

- Before：用户"提交推送"→ `git add . && git commit && git push`，把用户改了一半的 `config.ts` 和 `.zcode/` 计划缓存一起提了上去。
- After：盘点足迹是 3 个文件（2 改 1 增）；`git status` 另有 `config.ts`（非足迹）和 `.zcode/plans/`。判定：`config.ts` 的改动被我新增模块引用（语义依赖，不带构建失败）→ 交用户裁决；`.zcode/` 归为工具产物，建议加入 .gitignore。用户选择"config.ts 整文件带上"。按路径 `git add` 4 个文件，`diff --cached --stat` 核对一致后提交；push 单独执行，确认 ahead 0；报告：提交 4 个文件、config.ts 系用户裁决带入、工作区仅剩 .zcode/（已加 ignore）。
