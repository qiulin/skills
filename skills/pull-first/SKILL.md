# 干活前先拉取（Pull First）

基于几天前的代码做分析和修改，冲突会在提交时才撞上，全部返工。动手前先对齐远程：更新拉在前面是预告，拉在后面是地雷。拉到更新不是终点——核对它是否动摇本会话已有的结论和修改，才是这个动作的价值。

## 何时使用

- 会话内首次准备改代码、做分析之前
- 搁置较久后恢复干活，上次对齐远程已不可考
- 用户说"先拉一下代码""pull 最新""对齐远程"
- 与 commit-push 配对：工作头部 pull-first 对齐，工作尾部 commit-push 入库

## 操作步骤

1. **摸底**。`git fetch` 后看三个事实：当前分支 behind 多少、工作区是否干净、本地有无未推送提交。更新处理方式取决于这三者的组合。
2. **决定拉取方式**：
   - behind 0 → 已是最新，直接干活；
   - 工作区干净 + behind > 0 → `git pull --ff-only` 干净快进，无冲突风险；
   - 工作区不干净 + behind > 0 → 带着未提交改动 pull 会把别人的改动和自己的半成品搅在一起——交用户裁决：先 stash / 先提交 / 放弃拉取。不做默认选择。
3. **核对更新的影响**。拉到更新后，看两样东西：`git log HEAD..origin/<分支> --oneline`（别人做了什么）、`git diff --stat`（动了哪些文件），然后对照本会话核三个维度：
   - **文件交集**：更新碰的文件，与我已分析、已修改、已写入方案的文件重叠吗？
   - **语义影响**：重叠之处，改动是否推翻或动摇既有结论——分析过的模块被重构、设计依赖的接口变了、评审基于的代码被替换？
   - **冲突风险**：本会话已有未提交修改时，与更新是否同文件同区域？
4. **按影响分诊**：
   - 无影响 → 明确报告"拉取 N 个提交，核对过文件交集与语义，与本次工作无关"，继续干活；
   - 有影响或无法判定 → 列出受影响的具体结论/修改（更新前 vs 更新后的差异点），交用户决策：重新分析受影响部分 / 推翻相关结论重来 / 维持原结论继续。替用户赌"应该没关系"是越权。
5. **报告**。对齐结果（几个提交、涉及哪些文件）、影响核对结论（无影响也要说核对过哪些维度）、下一步动作。

完成标准：干活前分支与远程同步，或未同步的原因与用户决策已被记录；拉到更新时附影响核对结论——"无影响"必须注明核对维度，不许拉完就说"好了"。

## 标志性追问

- "我上一次和远程对齐是什么时候？"
- "更新的文件，和我已经分析/修改过的文件有交集吗？"
- "这个更新动摇了我已有的哪个结论？"
- "带着这些未提交改动 pull，安全吗？"

## 失败模式

- 从不拉取：整个会话建立在过期代码上，提交时才撞冲突，分析修改全部返工。
- 拉完不看内容：`git pull` 成功就开工。别人可能恰好重构了你正要分析的东西。
- 更新来了不核对：机械报告"已更新"。"拉下来"没有价值，"核对过影响"才有。
- 脏工作区盲目 pull：merge 自动混合别人的改动与自己的半成品，出了问题说不清谁是谁。
- 硬对齐：本地有未提交工作时用 `reset --hard` 对齐远程，直接毁掉工作。未提交的东西永远先安顿再拉取。

## 与相关 skill 的衔接

- commit-push 是工作尾部的对齐，本 skill 是工作头部的对齐，一前一后成对使用；
- 影响核对的方法（前提是否还成立、结论是否被动摇）来自 critical-thinking；
- 受影响的分析结论需要重做时，按 rethink 的换视角方式重新过一遍，而不是原样重复。

## 示例

- Before：会话恢复后直接继续改 `export/` 模块，提交时才发现远程已有人重构了导出入口，冲突 + 分析作废，全部返工。
- After：动手前 fetch——behind 3，工作区有本会话 2 个未提交文件。看 log 与 diff --stat：3 个提交动了 `export/writer.py` 与构建配置；核对——与未提交文件重叠（冲突风险），且本会话早前"导出入口在 main.py"的结论已失效（语义影响）。两项都影响 → 交用户决策。用户选"先 stash 再 pull，重新确认入口后恢复"。拉取后报告：3 个提交、入口已迁至 `export/entry.py`、原结论标记作废、冲突点 1 处待处理。
