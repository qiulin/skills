# 批判性思维

先质疑，再推理，后解答。问题本身往往比答案更值得审：带着错误前提的问题，认真回答就是认真犯错。

## 何时使用

- 用户的问题内嵌了未经检验的前提（"为什么我们的服务比竞品慢？"——真的慢吗？）
- 引用了结论、数据、"据说"，需要核实来源
- 分析、比较、归因类请求
- 排查 bug 时的归因假设

## 操作步骤

1. **质疑前提**。把问题拆成"前提 + 问句"，对每个前提问：
   - 事实性前提：有证据吗？查了之后还成立吗？
   - 概念前提：关键词有明确定义吗？（"慢"指 p99 还是均值？哪个接口？）
   - 框架前提：问题框定的选项穷尽了吗？有没有被排除在外的第三选项？
2. **交代质疑结果**。前提成立的说"前提确认过"；不成立的直接指出并改写问题——回答一个被修正过的问题，好过准确回答一个错误的问题。
3. **推理**。从已验证的事实出发逐步推导，每一步注明依据（源码位置、文档、测量结果、明确标注的假设）。跳步的地方写明"这里依赖假设 X"。
4. **解答**。只交付推理链条撑得住的部分，并区分三种状态：已验证（本次查证过）、推断（从事实推出，附推理路径）、猜测（缺证据的方向，附如何验证）。
5. **复核**。回头看一眼：推理链里有没有循环论证（用结论证明前提）、有没有把"相关"当"因果"、有没有幸存者偏差。

完成标准：回答中每个结论能标出已验证/推断/猜测之一；被推翻或修正的前提有明示。

## 标志性追问

- "这个问题的前提本身经过验证了吗？"
- "除了 A 导致 B，还有没有 C 同时导致 A 和 B？"
- "我是在验证假设，还是在寻找支持它的证据？"

## 失败模式

- 直接作答：跳过质疑环节，在错误前提上构建精致的长答案。
- 质疑变杠精：质疑的产出是修正后的问题和更可靠的回答，不是用"再想想"拒绝回答。
- 确认偏误：只收集支持第一直觉的证据。每形成一个假设，主动找一条能推翻它的证据。

## 示例

- Before："为什么我们的服务比竞品慢？"→ 开始分析架构差异。
- After：先质疑——"慢"有测量吗？压测显示 p50 相同、p99 高 4 倍且集中在写路径 → 前提修正为"为什么写路径 p99 高" → 推理：写路径独有同步双写（源码 L88）→ 解答（推断）：p99 尖刺来自缓存写超时重试；已验证：关掉重试的灰度中 p99 回落。
