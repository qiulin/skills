# 奥卡姆剃刀

如无必要，勿增实体。能同样解决问题的方案里，组件更少、假设更少的那个更可能正确、必然更好维护；要为复杂性付费之前，先证明简单方案已被排除。

## 何时使用

- 多个候选方案（或候选解释）之间做选择
- 设计评审中发现层次、抽象、配置项越来越多
- 排查 bug 时在多个可能原因之间判断
- 需求讨论中范围不断膨胀

## 操作步骤

1. **列出候选**。把所有能想到的方案（或解释）平铺，先不评价。
2. **清点实体**。数每个候选引入的东西：新组件、新依赖、新概念、新假设、新步骤，写成可数的清单——"感觉更简单"不可靠，数出来才可靠。
3. **对照约束**。逐一检查每个候选是否满足全部已知约束。关键动作是：要说"简单方案不行"，必须具体指出哪条约束、什么证据；说不出就默认简单方案可行。
4. **裁决**。满足约束的候选中，选实体最少的。复杂性只有一种获得方式：证明更简单的方案明确无法满足某条硬约束。
5. **为每个新实体记账**。方案里每引入一个组件/概念，写一句"它解决什么问题、不引入它会发生什么"。指认不出来，就删掉它。

完成标准：选型结论附带"被淘汰的更复杂方案 + 淘汰原因（哪条约束/什么证据）"。

## 标志性追问

- "不引入它，最坏会怎样？"
- "这个抽象有几个使用者？"（只有一个，它就是提前优化）
- "这个解释需要我额外相信几件没证据的事？"

## 失败模式

- 简单癖走向简陋：剃的是"无必要的实体"，必要的复杂度（安全、一致性、错误处理）是约束的一部分，不在剃除之列。先数约束，再数实体。
- 用"以后可能需要"引入实体：未来需求是猜测不是约束。等它真的出现再加，成本通常更低。
- 剃掉解释力：两个解释覆盖的事实集不同时，选覆盖全部事实中假设最少的，而不是无条件选字数少的。

## 示例

- Before："为了将来支持多租户，先抽象出 TenantProvider 接口、配置中心和租户路由表。"
- After：清点实体——3 个新组件，解决的是"将来可能"而非"现在必须"；约束里没有多租户，砍掉，单租户直连实现。多租户真到那天，基于真实需求重新设计的抽象，比现在猜出来的更贴合。
