# 高内聚低耦合

内聚看变化原因：一个模块内的代码应该因为同样的原因、在同样的时间变化。耦合看传播半径：改 A 时被迫改动的模块越少越好，依赖方向最好是单向的。

## 何时使用

- 划分模块、包、类、函数的边界
- code review 中出现"这个文件不知道为什么引了那个"
- 重构：重复代码、万能 utils、上帝类
- 纠结"这段逻辑放哪里"——判断依据是变化原因，不是代码长度

## 操作步骤

1. **列变化原因**。枚举系统会变化的需求类型：换存储、改协议、新计费规则、新终端……给每个模块标注它会因哪些原因变化。一个模块对应恰好一组原因 = 高内聚；对应多组 = 该拆。
2. **画依赖方向**。列出模块间的引用关系，检查两点：
   - 方向是否指向更稳定的一侧（领域逻辑 > 应用服务 > 适配层/工具）；
   - 是否有环：A→B→A 的环意味着两边揉在同一个变化原因里，从公共处拆开，或引入单向接口。
3. **切分/归并**。
   - 多个变化原因挤在一个模块 → 按原因拆开，各自收敛；
   - 两段代码总因同一个原因一起变 → 合并，消除跨模块同步修改；
   - 没有内部状态、不引用领域概念的纯工具 → 沉到最底层。
4. **耦合自查**。对每个跨模块调用问：传的是对方需要的最小数据，还是整个对象顺手扔过去？改动一个接口签名会波及几个模块？
5. **验收**。用"改一个需求需要动几个文件"检验：拿一个近期真实需求复盘，或假设"换掉存储引擎"数一遍波及面。波及面超出该变化原因所属的模块，设计还没到位。

完成标准：每个模块能用一句话说清职责和它的变化原因；依赖图无环且指向稳定侧。

## 标志性追问

- "这个模块会因为什么原因被修改？"（答不出或答出多个 → 内聚有问题）
- "改这里，下游谁会被迫跟着改？"（答不清 → 耦合有问题）
- "这两段代码会一起变吗？会 → 合并；不会 → 拆开。"

## 失败模式

- 按技术分层切业务：所有 service、所有 dao 各一个大文件，任何业务改动都要横穿所有层。层的边界服务于变化原因，不是名词分类。
- 过度拆分：为了"小"把强相关的逻辑拆到十几个文件，改一个需求跳十处。拆的依据是变化原因不同，不是行数。
- 用 utils 吸纳一切：utils 变成万物依赖 = 最高耦合点。工具函数下沉为稳定底层，业务逻辑按变化原因归位。

## 示例

- Before：`utils.py` 里既有发短信、又算佣金、又解析日期。任何需求都改这个文件，所有人都 import 它。
- After：按变化原因拆——`notify/`（渠道会换）、`commission/`（规则常改）、`dates/`（稳定工具，沉底）。换短信供应商只动 `notify/`；三个模块互不依赖。
