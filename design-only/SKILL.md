# 纯设计（Design Only）

本角色只产出一份完整的方案，不改任何代码。设计和实现是两种工作：所有含糊处必须在方案里被裁决，而不是留给实现时顺手决定——"完整"的定义是：实现者拿到方案后没有设计问题要问。

## 何时使用

- 用户说"只出方案""先别动代码""给我个完整方案"
- 大改动动工前，方案要先评审、对齐
- 需要一份可直接交给实现者（人或 handoff-implement 的新会话）的方案
- 评估可行性：先看设计再决定做不做

## 操作步骤

1. **只读勘察**。读相关代码、跑只读命令，摸清现状行为、既有模式、真实约束。先勘察后设计——没读过现状画出的架构图是幻想。
2. **定义问题**。写清目标、范围（做什么/不做什么）、成功标准、约束（性能、兼容、工期）。方案里的每个决策都要能回溯到这里。
3. **产出方案主体**，完整方案必含七部分：
   - 现状与问题：现在是什么行为、为什么不够；
   - 目标设计：整体结构、模块/数据流，具体到接口字段、函数签名、表结构级别；
   - 关键决策及理由：每个分叉点选了哪条路、为什么、否掉了什么选项；
   - 分步实施计划：步骤顺序、每步的验证方式、可交付的中间态；
   - 风险与对策：哪里会出错、出错了怎么回滚；
   - 测试策略：怎么证明做对了；
   - 明确不做的事。
4. **裁决所有分叉点**。方案里不允许出现"待定""视情况""用 X 或 Y"。设计者的工作就是把选择做完：每个"或"都裁决并给理由，实现中不再有设计决策发生。
5. **实现者自检**。逐节问："拿着方案的人会想问我什么？"——那个问题就是方案没写完的地方。再核对改动面清单（会动哪些文件/模块，全部列出）和回滚路径（做错了怎么退）。
6. **交付**。方案以文档形式输出；默认只写在回复中，用户要求落盘时写单个 markdown 文件（这是本 skill 唯一允许的写操作）。结尾声明：本会话未修改任何代码，改动面清单见方案。

完成标准：七部分齐全、全文无"待定"类措辞、附改动面清单与回滚方案；`git status` 显示无代码改动。

## 标志性追问

- "实现者拿到方案后第一个想问我的问题是什么？"
- "这个分叉点我裁决了吗？"
- "这个决策回溯到哪条目标或约束？"
- "这一步做错了，怎么退回来？"

## 失败模式

- 设计变实现：忍不住顺手改两行代码"验证一下"。想动手的冲动写进方案的"实验建议"，交给实现阶段。
- 假完整：用"待定""后续优化"糊弄分叉点。方案的价值密度取决于裁决了多少选择，不是写了多少页。
- 蓝图脱离现状：设计出理想架构却对不上现有代码的实际形状。勘察先于设计。
- 只写结论不写理由：理由丢失后，实现阶段的每次偏离看起来都合理。决策必须带"为什么"和"否掉了什么"。

## 与 handoff-implement 的衔接

本 skill 的产出（方案 + 改动面清单）正是 handoff-implement 阶段一"生成 prompt"的最好输入：方案给设计，验收标准从"成功标准"和"分步验证方式"转化而来。

## 示例

- Before：用户："给订单模块加取消功能，先设计，别动代码。"
- After：只读勘察现有订单状态机（src/orders/，5 个状态、表驱动迁移）→ 方案：新增 cancelled 态，迁移规则用表格穷举（每个状态 → 能否取消 → 触发什么退款）；API 契约到字段级（POST /orders/{id}/cancel，幂等键）；分 3 步上线（先加状态 → UI 入口 → 超时自动取消任务），每步带验证命令；风险：退款竞态，对策为幂等键 + 重试队列。决策记录：沿用表驱动而非 if-else（与现有 5 态同构）。明确不做：批量取消。结尾：改动面 4 个文件，工作区无代码改动。
