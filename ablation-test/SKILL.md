# 消融实验

一个东西是否必要，不靠争论，靠拿掉试试：拿掉之后系统仍满足需求，它就是多余的；拿掉之后坏了，它才有存在的资格——并把理由写下来。

## 何时使用

- code review 中怀疑某段代码、某个依赖、某条配置多余
- 流程/方案步骤多，想确认哪些环节真正产出价值
- 调试：定位是哪个组件引入了问题
- 写作/论证：某个论据是否真的支撑结论

## 操作步骤

1. **圈定候选对象**。明确拿掉什么：一段代码、一个依赖、一个中间层、一个流程步骤、一个参数。一次只拿掉一个，否则无法归因。
2. **定义"仍正常"的判据**。拿掉之前先写下通过标准：哪些测试要过、哪些场景要走通、结论是否仍成立。没有判据的消融只是随手删代码。
3. **执行拿除**。删掉（或注释掉）目标对象。物理删除优于"逻辑上绕过"——绕过常常留了半条依赖路径，测不出真话。
4. **验证**。跑测试、走关键路径、重推一遍逻辑。观察要覆盖候选对象原本声称服务的场景。
5. **裁决并留痕**。一切正常 → 删，本次实验的结论就是删除依据；坏了 → 恢复，并在注释或文档中写清"它存在是因为 X"，让下一个人不用再猜。

完成标准：每个候选对象都有明确判定（删/留）和对应的验证记录。

## 标志性追问

- "这行/这个依赖/这个步骤删了，测试还过吗？"
- "它坏的时候我们会知道吗？"（拿掉后无感，多半本来就没被依赖）
- "当年加它是为了什么？那个问题还在吗？"

## 失败模式

- 一次拿掉多个：坏了不知道怪谁，好了不知道功劳归谁。
- 判据缺失："看起来没问题"就删。必须先有可执行的验证手段。
- 只做静态推断："这行没被引用，删了肯定没事"——动态条件调用、反射、配置引用都会让静态推断翻车，以运行结果为准。

## 示例

- Before："这个 util 函数应该没人用了吧？"→ 留着（怀疑不产生结论）。
- After：全局搜索确认 + 删除 + 跑全量测试 → 全绿，删除并记录；或某个夜间任务报错 → 恢复，注释写明"夜间对账任务依赖，见 ops#123"。
